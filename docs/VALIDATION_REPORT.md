# Validation Report

SIH26150 · DVR/NVR Forensic Analysis Tool · state of `main` after the last commit before this report.

## 1. Summary — read this before anything else

| Question | Answer |
|---|---|
| Has the tool been validated on a **real DVR/NVR disk**? | **No.** No real recorder disk was available. |
| What was validated, then? | The software's behaviour on **disk images we built ourselves** from published format descriptions and from **real ffmpeg-encoded video**, plus the forensic bookkeeping (hashing, audit, reports, auth). |
| Can any recovery rate or accuracy be quoted for real recorders? | **No.** Numbers from synthetic disks describe our test disks, not recorders. |
| Automated tests | **262 passing** (254 without a live Supabase connection; the other 8 exercise the Postgres backend). 59 of them are security tests (headers, Host/Origin, audit seal, encryption, 2FA, signing, sandbox, parser fuzzing). |
| Trust level of every vendor format (see `format_verification.md`) | **L2 at best** (corroborated by sources and tested on synthetic data). **None is L3** (validated on a real disk). |

This report therefore documents *verification* (does the code do what it is specified to do) and does **not** claim *validation* (does it work on the real thing). Section 7 gives the protocol for turning it into real validation.

## 2. Scope and method

- **Unit and integration tests** (pytest) using disk images generated by `backend/test_images/gen_test_image.py` and by per-test builders that embed real video.
- **Known-answer tests**: parsers are fed the byte values printed in the source papers/specifications and must return the printed interpretation.
- **End-to-end manual scripts** (`backend/tests/manual/`): build a disk around a real H.264 video of a person (AI-generated portrait photos, gitignored), scan, export, run face detection, and compare with a reference photo (match) and a different photo (no match).
- **Ground-truth accuracy tests** using the tool's own accuracy module on real video (identical, truncated, different, perceptual, log coverage, byte placement).
- **UI checks** in a browser against an isolated server (database disabled, throw-away password), including drive imaging of a file, object detection, and the accuracy card.

Independence caveat: the disk builders and the parsers were written by the same team from the same sources, so a shared misreading of a source would not be caught. This is why real-disk validation is mandatory before any operational claim.

## 5. Defects found by testing

| Finding | How found | Fix |
|---|---|---|
| Dahua export failed on real video — DHAV constants (frame types, header layout, date encoding) were wrong | End-to-end export of real video | Re-derived from FFmpeg `dhav.c`; corrected constants and date bitfield |
| Verify failed after a server restart ("Evidence image is not loaded") | Manual UI test | Verify re-opens the evidence by its stored path |
| Hikvision carver absorbed junk after a decoy SPS; and a blanket duplicate trim truncated real slices | Decoy-stream tests | SPS/PPS size guard; duplicate trim applied to the last slice only |
| Old Honeywell stub tests contradicted a real implementation | Test failures after the rewrite | Tests rewritten with the paper's known-answer bytes |
| **Tiny P-frames of static scenes were rejected (`DHAV_MIN_FRAME_BYTES = 100`), so only 21 of 40 frames were carved (byte recall 86.5 %)** | Placement/recall check against ground truth | Lowered to 40: 40 of 40 frames carved, byte recall 92.1 %, placement precision 100 % |
| Test suite once wrote fixture rows into a live Supabase project | Reviewing the database | `DATABASE_URL=""` forced in `conftest.py`; a guard asserts the real case folder is never used |
| Format sheet mislabelled paper-derived facts as "AI report" | Reading the paper in full | Sheet corrected; MDPI "HKVI" frame format rejected as uncorroborated |

## 6. What has not been validated

1. Any parser on a real recorder disk (Dahua, Hikvision, Honeywell, CP Plus).
2. Any vendor format for TP-Link, Godrej, Uniview, Matrix (not implemented; no public source).
3. Behaviour on real deletion, overwrite, wear and fragmentation patterns.
4. Drive imaging on a physical device (size discovery, aligned raw reads, admin rights).
5. Object and face analytics on real CCTV footage (low light, small subjects, compression).
6. Performance and memory on multi-terabyte images (not benchmarked).
7. Timestamp correctness against a recorder's own clock and time zone.
8. Legal admissibility of the report and certificate (a template; needs counsel).

## 7. Protocol to validate on a real recorder

Run this once per vendor and model; record everything in the results table.

1. **Prepare.** A recorder with a spare disk, a hardware write blocker, and a second disk of equal or larger size for images.
2. **Record ground truth.** Record a scripted scene (a person walking in, a card with the current time held to the camera) for a known duration on 1–2 cameras. Export the same clip with the vendor's own player and keep it as the *ground-truth video*. Note the recorder's clock and time zone and write a *recording log* (JSON, `docs/accuracy_measurement.md`).
3. **Image before deletion.** Remove the disk, image it behind the write blocker (`imaging.py` or an accepted forensic imager), record both hashes. This is the *original image*.
4. **Delete.** Return the disk, delete the recording through the recorder's menu (and, as separate runs, format/initialise it and let it overwrite). Image again: the *deleted image*.
5. **Recover** the deleted image with the tool. Record brand detected, confidence, segments, statuses, and notes.
6. **Measure** with *Accuracy Against Ground Truth*: supply the ground-truth video, the log, and the original image path. Record frame recall, precision, order, byte-identical, log coverage, byte recall and placement.
7. **Decode check.** Watch the export; confirm the time card matches the recorder's clock and the person is visible; run faces/objects.
8. **Repeat** with a longer recording, several cameras, and a fragmented (long-running, partly overwritten) disk.
9. **Promote or demote** the format in `docs/format_verification.md`: L3 only if the offsets and fields were confirmed on the real disk; document any field that differed and fix `constants.py`.

## 8. Conclusion

The software components are verified against their specifications and against synthetic disks built around real video, and the forensic bookkeeping works as designed. **The project cannot yet claim to recover evidence from real recorders.** The single most valuable next step is the protocol in §7 on at least one Dahua/CP Plus and one Hikvision recorder.
