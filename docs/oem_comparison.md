# DVR/NVR OEM Comparative Analysis

This comparison is deliberately conservative. It distinguishes a confirmed on-disk signature from a brand label and does not turn unverified research into a recovery claim. The Dahua and Hikvision entries below are derived from this repository's format sheets.

All eight OEMs named in the SIH26150 problem statement now have a registered plugin (see `backend/plugins/`), so none are silently absent from detection or the report. Registering a plugin is not the same as implementing recovery: for five of the eight, the plugin is an honestly-labelled detection-only stub that never claims a verified format match and cannot carve video. Turning a stub into a real parser requires a publicly documented format or a representative real-disk sample to validate against — guessed offsets are refused by design (see "Evidence basis and limits" below).

| --- | --- | --- | --- |
| **Dahua Technology** | **DHFS 4.1** is documented for DVR/NVR use; some NVR media may use XFS or mixed DHFS/XFS. The recoverable stream format documented here is **DHAV**, with `DHAV` frame starts and `dhav` frame footers. | The DHFS index layout is not implemented or fully verified, so recovery relies on carving. Timestamp epoch/timezone and several header fields remain unverified. Interleaved multi-camera streams must be grouped by channel and time; proposed segmentation thresholds need validation on real media. | **Supported.** The Dahua plugin detects and carves DHAV content; it does not claim verified DHFS index parsing. |
| **CP Plus** | No CP Plus-specific file system or container is verified. The Dahua format sheet records only an unverified compatibility hypothesis: a CP Plus disk containing **DHAV** frames can be handled as Dahua-formatted content. | A CP Plus nameplate does not establish a Dahua-compatible disk. Detect from the actual disk signature; non-DHAV media needs a separate validated parser. | **Conditional carving via Dahua compatibility.** `CPPlusPlugin` detects the CP Plus marker and, when DHAV frames are also present, routes carving through the Dahua engine — frames are tagged `brand="cpplus"` (not `"dahua"`) and segments stay `UNCERTAIN` with an explicit unverified note; there is no native CP Plus filesystem/container parsing. |
| **Hikvision** | A master-sector signature, `HIKVISION@HANGZHOU`, is documented at disk offset `0x200`; the index is named **HIKB-TREE**. Video is described as standard H.264/H.265 NAL-unit content. | The HIKB-TREE entry layout is not verified or implemented, and it is unverified whether real Hikvision data blocks hold raw H.264, MPEG-PS (FFmpeg's `mpeg.c` confirms Hikvision export files are MPEG-PS), or a private wrapper. Channel and timestamps are therefore unavailable. | **Standards-based carving, decode-validated.** Detection is implemented. The carver recovers contiguous MPEG-PS and H.264 Annex B streams from public-standard structure (byte-exact and decodable on real ffmpeg-encoded test video, with decoy rejection — see `docs/format_sheets/hikvision.md` §5). Results start **UNCERTAIN**, become **PARTIAL** only if ffprobe decodes the export, and are never **COMPLETE**. Not validated on real Hikvision hardware; index reading is not implemented. |

## Evidence basis and limits

- Dahua facts and limitations are taken from [`format_sheets/dahua.md`](format_sheets/dahua.md); items marked "TO VERIFY" there are not a basis for a forensic claim.
- Hikvision facts and limitations are taken from [`format_sheets/hikvision.md`](format_sheets/hikvision.md). In particular, the documented master-sector detector is not proof that a recovered stream is complete or admissible.
- The Honeywell, TP-Link, Godrej, Uniview, and Matrix stubs are intentionally not populated with guessed formats, offsets, brand relationships, or recovery claims — their `detect()` markers are unverified vendor-name ASCII strings only, deliberately capped below the confidence needed to attempt carving. Move an OEM from "detection-only stub" to "supported" only after a public source or a representative real-disk sample supports the specific offsets/format implemented — not before.
